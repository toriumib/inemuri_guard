# 時計センサーモード設計（居眠りガード × スマートウォッチ）

カメラなしで眠気を検知する「時計をセンサーにするモード」の設計メモ。
未実装。フェーズ1（時計への通知転送）だけ実装済み。

## 経緯と現在地

| フェーズ | 内容 | 状態 |
|---|---|---|
| 1 | 眠気検知→スマホの通知→Wear OS が時計へ自動転送（振動） | **実装済み**（設定「時計にも通知(β)」） |
| 2 | 時計側で生体信号から眠気を推定し、落ちる前に起こす | この文書。設計のみ |
| 3 | 時計単体で完結（スマホ不要） | 構想のみ |

フェーズ1の実装メモ:

- 転送は Wear OS の標準ブリッジ。専用の時計アプリ・SDK は不要。
- オフ時は通知に `FLAG_LOCAL_ONLY`（0x100）を付け、システムへのブリッジを止める。
- 通知のバイブは `[0, 700, 350, 700, 350, 700]`。1回の短い buzz は手首では
  寝ていて分からないため、「起こす」を意図した反復パターン。
- 設定キー: `watch_bridge_beta`（SharedPreferences、既定 ON）。

### フェーズ1の検証記録（2026-09-04、エミュレータ）

エミュレータ(Pixel 6a / API 35)で dart-define の検証フック
（`FIRE_NOTIFICATION_TEST=true` の debug ビルドのみ、起動3秒後に1通発火）を使い、
`dumpsys notification --noredact` で通知レコードを直接確認した:

| 設定 | flags | 意味 |
|---|---|---|
| bridgeToWatch=true（既定） | `ONGOING_EVENT\|HIGH_PRIORITY` | LOCAL_ONLY なし → 時計へ転送される |
| bridgeToWatch=false | `ONGOING_EVENT\|HIGH_PRIORITY\|LOCAL_ONLY` | 時計への転送が止まる |

設定UIのトグルが SharedPreferences の値と双方向で一致することも確認。

**Wear OS エミュレータとの実ペアリングは未検証。** 検証するには:
スマホ側エミュレータに Play Store から「Wear OS by Google」コンパニオンアプリを
入れ（Google アカウントへのサインインが必要）、アプリ内の ⋮ →「エミュレータと
ペア設定」。Wear AVD（`wear4` = android-33 / android-wear / x86_64）は作成済み。

### 検証中に見つけて直したこと（リリース品質に関わる）

1. `main()` が `await adService.init()`（MobileAds 初期化）を待っていた。
   Play services が不調な環境でこの await が戻らず、通知・UI を含むアプリ全体が
   スプラッシュのまま止まるのを確認した。**広告初期化をノンブロッキング化**した。
   広告は準備できたものから載る。
2. `AlarmService.start()` が音声の初回再生を await してから通知を出していた。
   音声初期化が環境で止まると、時計への転送も引きずられて遅れる。**通知を最初に
   投げてから音を鳴らす**順に変えた（エミュレータで実際に止まるのを確認）。

## フェーズ2: 時計を眠気センサーにする

### 動機

カメラ版の前提は「スマホを立てて顔を映す」。これは自席では成立するが、

- 立ち仕事・移動中・ソファなど、カメラを置けない場面がある
- 「顔を映され続ける」ことに抵抗がある人もいる

手首にいる時計なら、この2つの制約が外れる。代わりに「まぶた」は見えない。
**見えている信号が変わる**ので、検知の設計も変わる。

### 使える信号と評価

| 信号 | 取得 | 眠気との関係 | 評価 |
|---|---|---|---|
| 心拍 (PPG) | `TYPE_HEART_RATE`、1Hz | 入眠移行で漸減。覚醒時の個人差が大きい | ◎ 連続取得が容易。**相対変化**で使う |
| HRV (RR間隔) | `TYPE_HEART_RATE` の RR 値 or `SensorManager` | リラックス→HF成分増。うとうとで上昇傾向 | ○ ノイズ多い。移動平均必須 |
| 加速度 | `TYPE_ACCELEROMETER`、~10Hz | 腕が動かなくなる＝静止。ただし読書・食事でも静止 | △ 単独では誤検知多。「静止が続いた」条件として併用 |
| 皮膚温度 | `TYPE_SKIN_TEMPERATURE` | 変化が遅く、環境に左右される | × 却下 |

### 検知の骨子（案）

カメラ版の「PERCLOS の蓄積」に相当するものを、心拍で作る:

```
baseline = 過去5分のHR中央値（モード開始後に自動構築）
drowsiness_score(t) = w1 * drop(HR, baseline)      # HR低下率
                    + w2 * rise(HF-HRV)              # HRV上昇
                    + w3 * stillness(wrist)          # 手首静止の連続時間
発火: score が閾値を N 秒超えたら「うとうと」と判定
```

- まばたき相当の「即時シグナル」は無い。**移行の検知**であり、
  カメラ版より早く、決定力は低い。感度は最初から3段階用意する。
- ベースライン構築中（最初の5分）は発火しない。UI で「ならしています」と出す。
- 手動で「起こされた」記録を学習データにする設計は**しない**（クラウド学習が要るため）。
  閾値は固定+感度設定のみ。

### アーキテクチャ

```
[Wear OS コンパニオンアプリ]
  SensorManager で HR/加速度を取得 → スコア計算（時計上）
  発火時のみ MessageClient → スマホへ "DROWSY" を1パケット
  ※生データは時計の外へ出さない。画面も出さない（常時黒画面で省電力）

[スマホ: 居眠りガード]
  WearableListenerService で受信 → 既存 AlarmService.wake() を流用
  スマホが圏外/非接続のとき: 時計単体で vibrator で起こす（フォールバック）
```

-時計↔スマホは Bluetooth の MessageClient。**クラウド・インターネットは経由しない。**
- コンパニオンアプリは Kotlin 単体で書く想定（Flutter Wear は今も発展途上）。
  スマホ側は既存の Flutter 実装に `WearableListenerService` の薄い橋を足すだけ。

### プライバシー方針（カメラ版と同じ線）

- 心拍・HRV・加速度は**時計上でのみ処理**。スマホへ送るのは発火の1パケットのみ。
- 生データの永続化なし。スコアリングに使う窓（~5分）だけメモリに持つ。
- 記録タブには「時計で検知」フラグだけ残す（既存の90日ルールに従う）。
- Health Connect / 健康 API には**書かない**（他アプリと生体データを共有しない）。

### 制約

- 対象は Wear OS（Galaxy Watch4 以降、Pixel Watch 等）。心拍センサーは
  エントリー機でもほぼ搭載されている。
- Apple Watch は別実装（WatchConnectivity + SwiftUI）になる。フェーズ2安定後に検討。
- HR 連続サンプリングはバッテリーを食う（実測して数時間程度を見込む）。
  「モード中のみ測定」で切り抜ける。充電しながる昼寝の想定と合う。
- **医療機器ではない。** 検知漏れ・誤検知の両方が起きる。UI に明記する。

### マイルストーン

- **M1**: コンパニオンの雛形。HR の生値をログ取得できること（開発用ビルドのみ）
- **M2**: スコアリング実装。スクリーンに数値を流すだけのデバッグ画面
- **M3**: MessageClient 往復。スマホのアラームが鳴るまで
- **M4**: 検知タブに「時計センサーモード(β)」UI。感度3段階
- **M5**: Play の同一アプリとして配布（コンパニオン配布は `wear_app` 扱い）
